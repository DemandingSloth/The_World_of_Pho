World of Pho — Guilds Feature: Implementation Plan
1. Goals & Constraints
* Stand-beside feature: does not modify existing marketplace, missions, garden/orchard, or mining code paths.
* Reuses the existing mission-tracking system rather than building a parallel one.
* New entry points: a "Guilds" button on the top bar and on the home screen.
* Backed by Supabase, consistent with the existing marketplace backend.

3. Mission Multiplier Logic
Given the stated formula:
* multiplier = (capacity + member_count) / 2
* target = base_target × multiplier


Resolved:
* Missions are generated through the existing player-mission generation logic (same base target, same random fluctuation the solo mission generator already applies) — no new fluctuation system.
* The guild multiplier ((capacity + member_count) / 2, kept as a decimal — not pre-rounded) is applied on top of that generated base target.
* The combined result is rounded once, at the very end, right before the mission is posted. So the order is: generate base target (with existing fluctuation) → multiply by decimal guild multiplier → round → post.
* Mission spawn cadence/frequency scaling ("pop in based on how many players/spots available") — recommend spawn rate (missions per day) scale with member_count, while spawn size scales with the multiplier above. These are separate knobs; conflating them will make balancing harder later.
________________


4. Token & Upgrade Point Distribution
On guild_mission.status → completed:
1. Sum amount_contributed across all guild_mission_contributions for that mission.
2. total_tokens_granted is a fixed pool (existing token-value table, keyed by difficulty).
3. Per-user token share = total_tokens_granted × (user_contribution / total_contribution).
4. Players with zero contribution receive zero tokens (per spec: "must participate to receive tokens").
5. total_upgrade_points_granted is banked directly to guilds.upgrade_points — not split per-user, since upgrades benefit the whole guild.
Recommend doing this in a Postgres function/RPC (complete_guild_mission(mission_id)) rather than client-side, so completion + payout is atomic and can't be double-triggered by two members' clients racing.

5. Guild Linking & Cross-Perk Application
For a guild with an active link to a guild of a different specialization:
* effective_bonus_to_linked_members = own_specialization_perk_value × (1 − cross_guild_reduction)


Resolved: cross_guild_reduction is itself an upgradeable guild stat, not a fixed constant:
* Starts at 20% reduction (i.e. linked members get 80% of the perk value) when a guild has never upgraded this track.
* Upgradeable in 10 levels, −1% per level, finalizing at 10% reduction (90% of perk value) at max level.
* This is a per-guild upgrade — each side of a link can be at a different level, so the reduction applied going from Guild A → Guild B members is A's reduction level, and B → A is B's own.
* Add this as its own guild_upgrades row, e.g. upgrade_key = 'link_discount', level 0–10, where effective reduction = 20% − level%.
Concretely, per the spec's example: a gardening guild with a 10% crop-growth reduction and a linked mining guild with a 12% mining-reward increase, both at the default (unupgraded) link-discount level, means the gardening guild's members get 12% × 0.80 = 9.6% mining bonus, and vice versa. Upgrading either guild's link_discount track independently improves what their own members receive from the link.
Implementation approach: compute effective perks server-side (a view or RPC, e.g. get_effective_guild_perks(user_id)) that:
1. Looks up the user's own guild's guild_upgrades.
2. Looks up any linked guild(s)' guild_upgrades, applies the discount factor.
3. Returns a merged perk table the client applies at point of use (harvest, sale, prospecting, etc.).
This keeps perk resolution in one place rather than scattering "am I linked, and to whom" checks across every gameplay system that reads a perk.

6. Community Garden Grid (10-Level Progression)
Resolved visibility: guild gardens are visible only to members of that specific guild via RLS. Members of a linked guild (e.g. a linked mining guild) do not get read access to the garden — the link only shares perk values, not the garden/expedition boards themselves. Same rule applies in reverse for expeditions (§2.6): a linked gardening guild cannot view a mining guild's expedition grid. RLS policy: SELECT on guild_garden_tiles/guild_expedition_tiles requires EXISTS (SELECT 1 FROM guild_members WHERE guild_id = tiles.guild_id AND user_id = auth.uid()) — no additional clause for linked guilds.
Store the level→dimensions lookup table (from the spec) as a static config, not computed at runtime — it's a fixed asymmetric sequence, not a formula:
* [
*   {"level":0,"width":5,"height":5},
*   {"level":1,"width":10,"height":5},
*   {"level":2,"width":10,"height":10},
*   {"level":3,"width":18,"height":10},
*   {"level":4,"width":18,"height":18},
*   {"level":5,"width":27,"height":18},
*   {"level":6,"width":27,"height":27},
*   {"level":7,"width":38,"height":27},
*   {"level":8,"width":38,"height":38},
*   {"level":9,"width":50,"height":38},
*   {"level":10,"width":50,"height":50}
* ]


On an upgrade, resize guild_gardens and insert new guild_garden_tiles rows for the newly-added columns/rows only (never touch existing tile rows — expansion is additive, so in-progress crops on existing tiles are undisturbed).
Open question worth flagging to the team: at 2,500 tiles max, per-tile Supabase rows for a single guild's garden is fine, but if this pattern is reused elsewhere at larger scale it may be worth batching tile state into a compact array/JSON column instead of one row per tile. For 50×50 it's not a problem either way.

8. Integration Point With Existing Tracking System
The one place this plan touches existing code is a single additive hook: wherever the current tracker records progress toward a solo/marketplace mission, add a check — "is there an active guild mission with a matching base_mission_key for this user's guild?" — and if so, also write a guild_mission_contributions row. This should be implemented as a listener on the tracking event, not an edit to the existing mission-completion logic itself, so solo missions remain fully untouched.
________________


9. Membership Lifecycle Rules
Resolved:
* First-ever join: a player who has never been in a guild before becomes a full member immediately on joining — no probation. They can contribute to missions and receive upgrade benefits right away.
* Rejoin cooldown: after a player leaves a guild and joins a different guild, they enter a probation period on the new guild before they can contribute to missions or receive that guild's upgrade perks — 48 hours normally, or 24 hours if the new guild is (at time of joining) linked to the guild they just left. This is a flat rule: it does not escalate or change based on how many times the player has switched guilds before — always 48h or 24h, never more. Track this with a guild_members.perks_active_at (or cooldown_until) timestamp column; gate both the tracker's contribution hook (§8) and the effective-perk RPC (§5) on now() >= perks_active_at.
* Leaving mid-mission: if a member leaves a guild while a guild_mission is still active, their existing rows in guild_mission_contributions are not deleted. If that mission later completes, they still receive their fair token share per the §4 formula, computed off their recorded amount_contributed — payout isn't contingent on still being a member at completion time. They do not receive upgrade points from a mission that completes after they've left (those are banked to the guild, not the individual), and if the mission never completes, no payout occurs (consistent with the existing "must participate to receive tokens" rule — participation was recorded, but payout only fires on completion).
* Suggested schema addition: guild_members gets a left_at (nullable) column rather than hard-deleting the row on leave, so guild_mission_contributions history stays queryable for the payout above even after the user is no longer an active member.
10. Suggested Build Order
1. Supabase schema (§2) + RLS policies (guild members can read their own guild's rows; only leader can write upgrades/links).
2. Guild creation/join/leave + roster UI.
3. Mission multiplier + spawn logic (§3), reusing existing mission catalog.
4. Contribution hook into existing tracker (§8).
5. Completion RPC + token/upgrade-point distribution (§4).
6. Upgrades/bonus screen, spending upgrade points.
7. Linking system + effective-perk resolution (§5).
8. Community garden (§6) — Supabase-backed grid, reusing existing garden tile UI components.
9. Mining community expedition (§2.6) — multiplayer minesweeper.
10. Leaderboards (separate design pass, per your note).
